# Basement Band

A local desktop recording app for jamming together. React/TypeScript draws the workspace, C#/.NET manages sessions, and a separate C++/JUCE process owns audio devices and VST3 plugins. No account, server, or cloud connection is required to record.

For Visual Studio, open **[BasementBand.sln](BasementBand.sln)** and select the **Basement Band desktop** profile, then press **F5**. See the [build and debugging guide](docs/BUILD.md) for prerequisites and the [architecture guide](docs/ARCHITECTURE.md) for extending the code.

## Run

The Windows development build is in `artifacts`. After dependencies and builds are available:

```sh
npm start
```

For a clean checkout, install Node.js 22+, .NET SDK 10, CMake 3.22+, and a C++20 compiler (Visual Studio C++ desktop workload on Windows; Xcode command-line tools on macOS). Then:

```sh
npm ci
npm run build:all
npm start
```

`npm run dev` starts the UI with hot reload and the already-built local services. `npm run package` produces an unpacked desktop distribution in `release` with a self-contained .NET backend. Build separately on each target OS/CPU. Linux also needs JUCE's ALSA, X11, font and OpenGL development dependencies. Windows has been built and tested here; macOS and Linux still need native build and device validation. On a clean Windows machine the Microsoft Visual C++ x64 runtime may also be required by the native engine.

## First session

1. Connect one audio interface. Open **Audio setup**, choose its driver, input and output, and click **Connect device**. ASIO and WASAPI are enabled on Windows; JUCE provides the platform audio backends elsewhere.
2. Assign Input 1 to Guitar and Input 2 to Bass. Arm both tracks using **R**. Add more audio tracks for additional interface inputs.
3. Use your interface's **direct monitoring** to hear your instruments. Click the red transport button to capture all armed tracks together. Press Space to stop.
4. Drag across the ruler to select a cycle range, or double-click an audio region to loop its length. **L** toggles cycle; **Space** plays/stops; **R** records/stops. Cycle is suspended during recording so a take is never silently overwritten.
5. Save a `.basement` session. Keep its adjacent `.basement.audio` directory with it when moving or sharing the project. **Ctrl/Cmd+S** opens Save. Imported files are copied into local session storage.

The app starts with two empty tracks. Screenshots generated by the visual test use explicitly synthetic fixtures; the real app does not pretend to have recorded audio.

## VST3

Select a track, open **Plug-ins**, and choose an installed `.vst3` bundle. This iteration supports **one stereo-compatible VST3 audio effect per track**, its native editor, bypass, and saved plugin state. Plugins process track playback; live input monitoring through plugins is not implemented yet. Recordings always contain the original input, so plugin processing is non-destructive.

The app does not supply amp simulations or an effects library. A private gain plugin in `native/TestGain.cpp` exists only to test hosting and is not copied into the app distribution. Windows plugins cannot run on macOS or Linux: users need a compatible build of their chosen plugin. VST2, AU, instruments, sidechains, plugin chains, automation, and plugin latency compensation are not implemented.

## Current boundaries

- Up to 32 mono input tracks from **one shared audio interface**, stored as separate 24-bit WAV files on the same sample clock. Imported audio can be mono or stereo. Multiple independent interfaces are not aggregated.
- Playback, seek, waveform display, track volume/pan/mute/solo, input routing, region deletion (select then Delete), and sample-clock cycle playback.
- 4/4 grid with 40–240 BPM. Changing tempo changes the grid; it does not time-stretch audio. No metronome/count-in yet.
- No MIDI/drum editor yet. No undo, region trimming/splitting, comping, or mixdown export yet.
- Files are decoded into memory for playback, with a 20-minute per-file limit. This is an initial implementation, not yet suitable for long production sessions. Raw recording streams to disk; stopping loads the take into memory. Avoid takes over 20 minutes.
- Input/output latency compensation is not implemented. Simultaneous inputs are aligned with each other, but overdubs against existing playback may need later timing adjustment. Hardware/driver latency and real guitar/bass plugin compatibility still require testing with an actual interface.
- Plugins share the native engine process. A faulty plugin can stop the engine; restarting is required. Completed WAV files remain on disk. Crash-isolated plugin scanning/hosting and recovery for interrupted WAV headers are future work.
- Control changes use a short lock; the callback never waits on it. If it cannot acquire the lock, or disk buffering overruns, a visible dropout warning is raised. A lock-free command queue is needed before claiming production-grade low-latency reliability.
- Session metadata is saved through a temporary file and rename. Audio assets are copied alongside it; this is not a fully transactional multi-file save. Keep backups for important work.

Unsaved recordings are stored under the app's user-data `Sessions` directory (on Windows, normally `%APPDATA%/basement-band/Sessions`). Deleting a track or region from the arrangement does not delete its original WAV.

## Verification

```sh
npm test
```

Build first. Tests drive the actual JUCE callback with deterministic sample buffers: two-channel recording, separate WAV files, matching sample counts, playback, mute/solo, cycle wrap within an audio block, VST3 load/process/bypass/state restoration, and C# portable session save/open with missing-media handling. They do not access the microphone. On Linux a GUI display (or Xvfb) is needed by JUCE's message loop. The VST3 test fixture is built by default and can be disabled with `-DBASEMENT_TEST_PLUGIN=OFF` for distribution-only builds.

`electron scripts/screenshot.cjs` captures the UI with a synthetic fixture into `artifacts/screenshots`. The main desktop process uses a sandboxed renderer, context isolation, a narrow preload bridge, and structured JSON control messages. Audio buffers never pass through JavaScript or C#.
